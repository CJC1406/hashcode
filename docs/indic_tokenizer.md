# Plan C: model-compatible Indic tokenization (tokenizer-only prototype)

**Status (2026-10-25):**
- **Done:**
  - a tokenizer-only prototype, implemented and tested;
  - real ByteME-derived candidate tokens, built from the approved Wikipedia 20261001 **training** split;
  - native Qwen3 token counts measured on the **Wikipedia held-out split**, which is the same source and **not independent**, and on hand-written fixtures.
- **Not done:**
  - **no independent evaluation**: the FLORES+ approvals are still all `false`, so the 20% target is **unverified on independent data**;
  - **no model**: weights, `torch` and training aren't available or approved;
  - **no inference, speed or quality measurement.**
- **Evidence sheet:** `results/indic_tokenizer/evidence.md`, generated by `experiments/indic_tokenizer/evidence.py` from the recorded files.
- **Separate from Plan A:** this track is separate from the ByteME storage codec. P1/P2a/P2b/P2c, their frozen vocabularies, results and criteria are unchanged; the P2c file is only read, with its SHA-256 checked.

## Why a different kind of ID
| | ByteME storage IDs (P1–P2c) | Plan C model token IDs |
|---|---|---|
| Purpose | compact storage, decoded back to UTF-8 | input to an LLM |
| ID space | the project's own 65,536-entry table | the model tokenizer's vocabulary (Qwen3: IDs 0–151,668), extended with new IDs **151,669 and up** |
| Seen by a model? | **never** | yes, after the model's embedding and output layers are extended and trained |

ByteME storage IDs are never passed to a model. Plan C uses the ByteME **vocabulary and pipeline** only to *choose* candidate strings. Those strings become new entries in the model's own tokenizer.

## Architecture and data flow
```
approved training corpus (Wikipedia hiwiki+knwiki 20261001, TRAINING split only; held-out split skipped)
   │  codec/p2c segmentation (single-script runs, aksharas) + frozen P2c vocabulary (sha256 1e12dc48…, read only)
   ▼
candidates.py   pool B "bytme": P2c learned entries + whole words starting with a P2c entry
                pool C "words": whole words only (ablation, no ByteME)
                score = frequency × (Qwen3 tokens − 1); NFC-stable only; strict K/2 Devanagari + K/2 Kannada
   ▼  manifest (outside Git: training-derived text), each candidate with its new ID, base IDs, frequency and score
hf_bpe.py       Qwen3 tokenizer.json (official file, sha256 aeb13307…) + candidates as added tokens (non-special,
                normalized; matched leftmost-longest after NFC, before pre-tokenization) → native token IDs
   ▼
evaluate.py     A (base) vs B (ByteME) vs C (words): tokens, tokens per sentence and per 1,000 chars, reduction %,
                exact round trip, ID validity, coverage, throughput
model_plan.py   embedding/output rows needed, tied-weight resize, memory, initialisation map (no model loaded)
scripts.py      script spans (Deva, Knda, Latn, Zyyy, Zzzz) for routing and reporting; scripts, not languages
```

## Verified facts
- **Base tokenizer:** Qwen3, the local `external/token-vldb2026/tokenizers/qwen3.json`.
  - Its SHA-256 `aeb13307a71acd8f…` equals the Git LFS ID of `Qwen/Qwen3-0.6B` `tokenizer.json` at revision `c1899de289a04d12100db370d81485cdf75e47ca`.
  - Licence `apache-2.0` (model card metadata). The model is not gated.
  - Byte-level BPE: 151,643 vocabulary entries plus 26 special tokens, so IDs 0–151,668.
  - NFC normalizer; GPT-style regex pre-tokenizer.
- **Model (public `config.json` only; weights, 1.5 GB, were not downloaded):**
  - `vocab_size` 151,936, which leaves 267 unused rows;
  - `hidden_size` 1,024; `tie_word_embeddings` true; bf16.
- **Pre-tokenization limits BPE merges:**
  - Qwen3's regex `\p{L}+` doesn't include combining marks, so `नमस्ते` is split into `नमस` `्त` `े` before BPE. New *merges* could therefore never form whole Indic words.
  - The prototype uses the tokenizer's **added-token** mechanism instead, which matches before pre-tokenization (tested). Extension tokens are matched leftmost-longest anywhere in the text, including inside longer words.
- **Normalization:** the base tokenizer normalizes to NFC, so non-NFC input (for example `e` + U+0301, or U+0958) doesn't come back byte for byte, even with the original tokenizer.
  - The evaluator reports `exact` and `exact_after_nfc` separately.
  - Candidates that aren't NFC-stable are excluded.
- **Special tokens:** they are never produced from text. Text such as `<|im_start|>` is tokenized as ordinary characters (tested).
- **No dependencies:** no tokenizer library, model framework or model weights are installed. `hf_bpe.py` is a dependency-free reader of the model's own `tokenizer.json`.
  - It reproduces Qwen's known encoding of `"Hello, world!"` → `[9707, 11, 1879, 0]`.
  - Its merge loop matches an independent simple reference on more than 400 random Indic, Latin and emoji pieces.
  - **Self-consistency:** every one of Qwen3's 151,643 vocabulary entries, encoded from its own bytes, comes out as exactly its own ID (100%; a permanent test). This checks the merge table and merge loop.
  - **It has not been checked against the reference `tokenizers` library**, which isn't installed. Small differences could remain in the regex split (Unicode tables, `\s` edge cases).
- **Vocabulary coverage:** only 71 Qwen3 vocabulary entries contain a whole Devanagari character, and only 25 a whole Kannada one. This is why A needs about 925 (Hindi) and 1,378 (Kannada) tokens per 1,000 characters on the held-out text.

## Results: Wikipedia held-out split (same source; NOT independent evaluation)
`results/indic_tokenizer/wikipedia-heldout-qwen3-k2048/summary.json`:
- **Data:** every non-empty line of the **10,586 held-out documents** (`sha256(doc_id) mod 20 == 0`), which candidate selection never read.
- **Checks:** the evaluator verifies the corpus files by SHA-256 against candidate manifest B, and that the held-out count equals the builder's skipped count.
- **Grouping:** lines are grouped by dominant script.
- **Publication:** aggregates only, after the text guard.

| Group | Lines | A tokens | B tokens (ByteME) | C tokens (words) | B reduction | C reduction | B: lines improved / worse |
|---|---|---|---|---|---|---|---|
| hi | 102,057 | 12,644,616 | 7,994,239 | 7,292,847 | **36.8%** | 42.3% | 94,536 / 0 |
| kn | 40,148 | 10,114,344 | 5,466,930 | 7,325,146 | **45.9%** | 27.6% | 37,570 / 0 |
| en (Latin-script lines) | 7,841 | 118,109 | 117,657 | 117,615 | 0.4% | 0.4% | 101 / 0 |
| mixed | 2,885 | 186,461 | 133,507 | 136,813 | 28.4% | 26.6% | 2,461 / 0 |

- **Round trips:** exact for all 154,459 lines in A, B and C, and every ID is valid.
- **The ablation splits by language:** words only (C) is better for Hindi; ByteME-derived (B) is much better for Kannada. That is consistent with Kannada's suffixes (`ಲ್ಲಿ`, `ನ್ನು`), which P2c's akshara-aligned subword entries capture.
- **Why this isn't independent:** it is the same source as the training text, with shared templates and topics, so these numbers are likely optimistic.
- **English:** extension tokens contain only Devanagari/Kannada characters, so text without them is tokenized exactly as by A (tested). A real English regression check still needs FLORES+ `eng_Latn`.
- **Python prototype time:** 181 s for A, B and C together.

## Model integration: blocked (plan only)
`model_plan.py`, for B at K = 2,048:
- the final tokenizer size is 153,717, more than the 151,936 rows, so the embedding must be resized;
- the embedding is tied, so one matrix grows by 1,781 rows, **+3.65 MB in bf16**;
- each new row is initialized as the mean of the base-token embeddings it replaces (mapping in `model-plan-bytme-k2048.json`);
- all checks pass: IDs are contiguous, above all special IDs, and each candidate encodes to its own ID.

**Not done, and not claimed:** loading, resizing, training, generation, stop tokens, batching, streaming, latency, speed or output quality.

**Needs:** approval to download Qwen3-0.6B (1.5 GB, Apache-2.0), `torch` and `transformers`, a GPU (or patience on an M3 with 8 GB), and licensed Hindi/Kannada training text for the new embeddings.

## Proposed target (not an approved criterion)
At least **20% fewer native input tokens than the unmodified Qwen3 tokenizer**, for Hindi and for Kannada, on approved independent evaluation data, with English regression reported. A token-count reduction alone does **not** show the model can use the new tokens. That needs the model stage.

## Evaluator fixes made during the readiness audit
- **Decontamination:** in `--spec` mode, the owner's decontamination decision is now acted on. `report-only` runs the exact-overlap check against the frozen training files and reports counts only (tested).
- **Staging:** results are staged outside the repository and moved into `--out` only after the text guard. Before, a tripped guard could have left text under `results/`.
